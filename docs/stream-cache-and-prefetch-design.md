# 通用回环代理与区间覆盖缓存

> 对应 issue #26 ③。实现位于 `lmedia/lmedia-stream`（模块与来源无关）、
> 接入方 `lmedia/lmedia-client` 的 `webdav` 包、展示方 `lplayer` 的进度条。

## 1. 要解决的问题

网络媒体源（WebDAV，以及以后的 Subsonic 等）经本机回环代理播放时，原有实现有三个体验问题：

1. **提取阈值按比例**：等到缓存到文件 30% 才提取元数据，长文件要白等几 MB。→ 改成固定 1 MB
   头部窗口（#26 ①），实测本机 FLAC 的元数据尾部偏移中位数 0.26 MB。
2. **缓冲不可见**：进度条只能看到播放头，看不到"还能播多久"。→ 用**缓存覆盖率**上报（#26 ②）。
3. **缓存只支持连续前缀**：向前跳转时要把中间被跳过的部分一起下完，否则缓存就不再连续；而"
   为了连续性"付的代价正是用户最反感的"卡在一个位置等很久"。→ 区间覆盖 + 优先级预取（#26 ③）。

## 2. 覆盖模型：连续前缀 + 固定分段

### 为什么不是"单文件 + 随机写"

`kotlinx-io` 的 `SystemFileSystem.sink()` 只支持追加（`append = true`），随机写要每个平台各写一遍
`expect/actual`（JVM/Android 用 `FileChannel`、Native 用 `fseek`、Wasm 用 IndexedDB）。分段文件用
纯公共代码就能实现，代价只是文件数变多。

### 存储布局

| 路径 | 含义 |
| --- | --- |
| `<root>/lmedia/<namespace>/audio/<key>.part` | 从 0 开始的**连续前缀** |
| `<root>/lmedia/<namespace>/audio/<key>/seg.<i>` | 固定大小分段，覆盖 `[i*segmentSize, (i+1)*segmentSize)` |
| `<root>/lmedia/<namespace>/audio/<key>/seg.<i>.tmp.<random>` | 写入中的临时文件，**不算覆盖** |

`<namespace>` 让不同来源共用同一套缓存实现且互不干扰（WebDAV 用 `webdav`）。

### 两个关键不变量

- **前缀始终从 0 开始且连续**：标签解析要的"从 0 开始的完整文件"（taglib 读内嵌封面）只能由它
  满足。因此**只有请求正好接在前缀后面（顺序播放）才继续往后接前缀**。
- **"分段文件存在" = "这一段完整可用"**：分段先写临时文件，写满后 `atomicMove` 改名。崩溃只会
  留下一个可忽略的临时文件，不会留下"记了却没写全"的假覆盖——不需要随机写，也不需要"文件长度
  就是真相"这类脆弱不变量。

### 覆盖 = 前缀 ∪ 已存在的分段

`coveredRanges(key, totalSize)` 把两者合并成有序、互不相邻的区间；`openSpan(key, start, maxLength)`
返回"从这个位置起连续可读的一段"（跨前缀/分段边界时长度自然截断）。代理按它服务：能读缓存就读，
读到空洞才去远端取、边取边发。

### 跳转时的落盘代价

分段必须写满才能提交，所以跳转点落在某分段中间时会把这一段的前面部分一起取下来（**上限一个
分段**）。这部分本来也是这首歌的字节，不算白取。若该分段的开头已经落在连续前缀里，则**从本地
补齐**（`StreamProxy.copyFromPrefix`），不为已有的字节再跑一趟网络。

## 3. 优先级调度

### 三档优先级

`nextFillRange`（纯函数，`StreamFillPlan.kt`）决定下一步补哪儿：

1. **播放头及其前瞻窗口**——播放卡住就是这里没到。窗口默认 4 MB（`DEFAULT_LOOKAHEAD_BYTES`）。
2. **从播放头往后顺序铺满**——"开播后主动缓存完整歌曲"。
3. **播放器跳过留下的空洞**——最低，随时可被前两档抢走。

`allowBackgroundFill()` 为 false（计费网络）时只做第 1 档；前瞻窗口为 0 表示第 1 档也不做。

### 播放头从哪来

播放器自己的 `Range` 请求就带着它当前的位置（`StreamProxy.notePlayhead` 在 `serveAudio` 里被调用），
不需要新增播放状态管线。

### 不挡住播放器

- **单 worker**：切歌时取消上一个 worker——同一时刻只补正在播的那一首，否则快速切歌会留下好几个
  worker 抢带宽。
- **规划在锁内**：worker 拿到 key 锁之后才读覆盖、决定补哪儿。等锁期间播放器可能已经把那一段补上
  了，锁外算好的计划会作废（会重复下载）。
- **每步只补一个分段**：播放器的请求最多等这一步。
- **锁是公平的**：`kotlinx.coroutines.sync.Mutex` 按 FIFO 授予，排队中的播放器请求先于 worker 的
  下一步被满足。
- worker 每步之间 `yield()`，让出执行机会。

### 曲库级预取

`ensureCached`（"把没听过的歌补全"）走同一套补齐机制、同样每步一个分段，但由数据源的
`backgroundFetchEnabled` 开关控制——**与"正在播的这首"分开**：后者只受网络门控
（`allowBackgroundFill = { !blockedByNetwork() }`），默认就该发生。

## 4. 进度展示：多段区间

覆盖一旦碎片化，`已缓存/总长` 这个单一比例就会骗人：从 10% 跳到 80% 后它显示"已缓冲 23%"，
而实际能一口气播到的是 80% 往后那一段。因此：

- 域层 `MediaSourceBufferProgress.bufferProgress` 返回 `List<BufferedRange>`（比例区间，有序不重叠）
- 空列表 = "没有可显示的信息"（不上报的源、远端没给总长、还没开始下载），UI 不必区分三种情况
- `SeekbarLayout` 的次级层逐段绘制，且仍然画在滑块**之前**——滑块盖住播放头左侧，露出来的正好是
  "已缓冲但还没播到"的那几段
- 比例按**字节**算（缓存本来就按字节落）；对 FLAC 这类近恒定码率音频与时间比例基本一致

## 5. 踩过的坑

- **`kotlinx-io` 的 `sink` 只支持追加**：这是整个分段设计的前提，见 §2。
- **分段写入必须临时文件 + 原子改名**：直接写目标文件会让"半段"看起来像"完整段"，缺的字节被算成
  已缓存，之后播放到那里就静默拿到错误数据。
- **`filledSize` 这个含糊的名字要拆**：`prefixSize`（连续前缀，给提取窗口/一致性判断用）与
  `coveredBytes`（总覆盖，给进度显示用）语义不同，混用会让"头部窗口到了没"判断错。
- **后台任务的规划必须在锁内**：锁外规划 + 锁内执行 = 重复下载（已在 §3 说明）。
- **测试里要能把后台 worker 关掉**：断言 `backend.fetched` 的用例必须传
  `allowBackgroundFill = { false }` 且 `lookaheadBytes = 0`，否则 worker 的取数会让断言变成不确定
  的（真并发，等条件而不是 sleep，见 `StreamProxyTest.awaitCondition`）。
