在线播放的缓存与元数据提取：现状 vs 目标

同一个需求，两种分层方式 —— 以及为什么"换一个源"从"要写一套"变成"给一个 URL"。

1现状：所有能力都长在 WebDAV 这一棵树上

播放器只认一个本机 http 地址；但在它下面，代理、缓存、提取、回写全部由 WebDavSource 自己编排。

播放器（Media3 / AVPlayer / VLC）
只知道 http://127.0.0.1:PORT/audio/{key}，不知道有缓存
↓GET + Range
播放层 resolveMediaData(audio)
向数据源要地址：source.dataSource.getMedia(audio)
↓MediaData.Url（源自己起的代理地址）
WebDavSource 内部（全部耦合在这里）
① getMedia / getPicture / getLyric
起代理、拼 URL；封面/歌词读自己的 metadataStore
↓ProxyBackend.resolve / fetch（每个源都要重写）
② WebDavProxy
Range 处理 + 一把 per-key 锁 + 前缀缓存 + LRU 淘汰
↓onCacheProgress(key)
③ WebDavExtraction
30% 读头 / 100% 读全（taglib）→ metadataStore → patchFlow → 库
↓WebDavCache（前缀追加）
④ WebDavCache
只能顺序追加：seek 到后面要先补齐前面全部
↓HTTP Range（WebDavClient）
远端（NAS / Apache / Nextcloud）
① 换源 = 重写一套 新源要自己实现 WebDavProxyBackend、起一次代理、算缓存键、写一份提取编排。
② 一把锁串行所有读写 整文件下载与播放 Range 抢同一把 per-key 锁 → 8 秒读超时（当前 bug 1）。
③ 前缀缓存 只能顺序追加，seek 到中间必须先把前面下完。
④ 提取是 WebDAV 专属 别的在线源拿不到"听过的歌自动补全时长/封面/歌词"。
唯一已经通用的一层 播放器只吃 MediaData.Url，Playback.currentBufferedPosition 也不关心来源 —— 这两处不用改。

2目标：缓存与提取独立成通用层，源只负责"给地址"

接入点只有一处：把源给的原始 http(s) 地址改写成代理地址。其余全部自动发生。

播放器（完全不变）
依旧只知道一个本机 http 地址
↓GET + Range
播放层 resolveMediaData —— 唯一接入点
MediaData.Url(origin) → cache.wrap(origin, identity) → 代理地址
同时注册：url → (sourceName, audioId, fingerprint)
↓代理地址（播放器无感知）
lmedia-cache（通用，不认识任何源）
LoopbackRangeServer
Range 解析 / 边下边发 / 分段随机访问 / 按段加锁（不再串行整文件）
↓CacheProgress(key, ratio, localFile, complete)
HttpOriginSource + SegmentStore
普通 HTTP Range 客户端直连 origin；分段缓存 + 配额/LRU
↓事件流（不再由源回调）
lmedia-extract（通用，按媒体身份工作）
MediaExtractionService
队列 / 去重(sourceName+audioId+fingerprint) / 30% 读头 · 100% 读全（taglib 原样复用）
↓产出 ExtractedAudioMetadata
三路发布
① 通用存档（时长/封面/歌词）　② audioPatches → 库　③ onExtracted → 源（可选）
↓HTTP Range（统一在 HttpOriginSource）
远端（任何 http(s) 音源）
① 新源零成本 只要 getMedia 返回原始 URL，缓存/时长/封面/歌词全部自动获得。
② 只有两类"额外一行" 需要认证 → 注册 headers；需要回写远端 → 实现 onExtracted。
③ 分段缓存 seek 到中间只拉那一段；锁按段/连接，bug 1 的争用自然消失。
④ 缓冲进度免费 缓存直接给出 cachedRatio，不需要每个源实现 bufferedProgress。

各层"知道什么 / 不知道什么"

层知道不知道（这正是解耦点）
通用缓存URL、字节、区间、进度这是哪首歌、哪个源、什么格式
通用提取媒体身份、本地文件、标签内容URL 怎么来的、怎么认证
数据源自己的协议、认证、目录结构缓存怎么落盘、提取怎么调度

3提取怎么跑：一次播放的完整时序

关键变化：触发者从"WebDavProxy 的回调"变成"缓存的通用事件"，接收者从"WebDAV 的提取器"变成"按媒体身份工作的通用服务"。

#谁做什么为什么这样做
1播放器 → 缓存 →GET /audio/{key}（Range） 命中已缓存段直接回字节；未命中才向上游拉，边发边存
2缓存 → 提取 →CacheProgress(ratio ≈ 30%) 替换掉原来 WebDAV 内部的 onCacheProgress
3提取 →取 localFile(key)，taglib 只读文件头 此时文件还不完整，只能拿 title / artist / album / track
4提取 → 库 →轻量 patch（audioPatches） 列表、详情页立刻能看到正确的歌名/歌手
5缓存 → 提取 →CacheProgress(complete = true) 整首下载完成，才能读封面与内嵌歌词
6提取 →taglib 读全量 → duration / cover / 内嵌歌词 与现在的 includeCoverAndDuration = complete 完全一致
7提取 → 存档 →ExtractedMetadataStore[(sourceName, audioId)] 缓存会被 LRU 淘汰，提取结果必须独立保存
8提取 → 库 →完整 patch（时长 + 封面标记） 进度条时长、封面请求立刻可用
9提取 → 源（可选） →onExtracted(audio, metadata) 只有需要远端同步的源才实现（WebDAV 写 /.lmusic/）
10UI →要封面：源自己的实现 → 通用存档兜底 源完全没写 getPicture，也能出图
为什么提取要依赖"媒体身份"而不是"缓存 key" 缓存 key 只是字节的地址（可能是 md5(url)），而提取结果要写回"某首歌"——所以改写播放地址时顺手把 url → (源名, 歌曲 id, 指纹) 注册给缓存，这是唯一需要新增的桥。

4逐项对比

维度现状（WebDavProxy）目标（通用缓存 + 通用提取）
缓存归属绑在 source/webdav 包独立模块
适配新源实现 backend + 起代理 + 算 key + 写提取编排返回原始 URL（认证类多一条 headers）
缓存模型前缀顺序追加分段随机访问
seek 到中间先补齐前面全部只拉目标段
并发一把 per-key 锁，下载与播放互斥按段/按连接加锁
提取触发代理回调（源内部）缓存通用事件
提取能力仅 WebDAV所有在线源
去重 / 30%·100%WebDavExtraction 内原样搬进通用服务（同一套逻辑）
封面 / 歌词兜底无，只认源自己的 store源之后多一层通用存档
缓冲进度每个源实现 bufferedProgress缓存直接给 cachedRatio
回写远端耦合在源里可选钩子 onExtracted
播放器侧两边完全相同，不需要改

5现有代码怎么搬（不是重写）

现在迁移后改动性质
WebDavProxyLoopbackRangeServer改名 + 上游从"接口注入"改成"直连 URL"
WebDavCacheSegmentCacheStore改名 + 前缀改分段 + 目录按源分层
WebDavRangeRangeHeader原样搬
WebDavProxyBackend + ProxyBackend(20 行)HttpOriginSource删除 per-source backend；只留一个 HTTP 实现
WebDavExtractionMediaExtractionService队列/决策/去重原样复用，只换输入来源
WebDavMetadataStoreExtractedMetadataStore改名 + key 改 (sourceName, audioId)
WebDavSource.onCacheProgress 编排删掉，改实现 onExtractedWebDAV 只剩远端同步这一件事
MediaData.Url 语义源返回原始地址，由接入点改写播放器侧无感
resolvePictureData / resolveLyricData末尾加一层通用存档兜底新增 fallback，源不实现也有内容

6边界与注意点

情况处理
公开 http(s) 音频零改动
需要认证（WebDAV / Subsonic / Jellyfin）改写地址时注册 headers（凭据留在代理侧，播放器看不到）
签名短时效 URL源提供稳定 cache key，否则每次签名不同 → 缓存永不命中
HLS / DASH 分片不走 taglib 提取；元数据交给源自己提供
本地文件 / content:// / MediaData.Bytes不改写，保持原路径
缓存被淘汰后重播指纹相同 → 命中已有提取存档，跳过重复提取
Web（wasm）无本地文件系统 → 缓存与提取整链禁用
提取线程低优先级 IO 队列、可取消；绝不与播放请求抢带宽/锁
